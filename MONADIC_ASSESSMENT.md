# Assessment: Monadic Architecture Spec v1.1 vs the PA_AMB Stage 4 Engine

- Spec: `MONADIC_ARCHITECTURE_SPEC.md` v1.1, 2026-11-12 (user suggestion, not imposition).
- Engine: Stage 4, TypeScript core, 16 modules, 18,650 lines, 456 tests passing, local commit `375e81b` (not pushed).
- Assessment date: 2026-11-12. Read-only; no code changed.

## Verdict in one paragraph

The engine already embodies all six primitive effects in typed-function form — Reader, State, Result, Option, Writer-trace, and List — but it has no formal monad system (no `Calc<A>` type, no map/flatMap/bind helpers, no unified `CalcError`, no `Readonly` contexts), and that is fine: the spec itself (§1 NOTE) says a production TypeScript system can implement the effects with typed functions and explicit result objects and does not need a monad-transformer library. The genuinely new work in the spec is not the monads but the conclusion propagation: the WorkProductLog as a monoidal Writer, FindingPublicationCalc, WorkProductContributionCalc, the shared WorkProductLedger, the R1 template section registry, R1AssemblyCalc, two-level provenance, the Image Viewer citation rules, and the G1–G14 gates. The R1 source check confirms the core facts (§3 AMB accept-and-support; "Image Viewer Document #123") but contradicts the spec on §18 (it exists) and finds the §8.2 product column and the §8.3 MUST list to be the spec author's inference, not PBGC-sourced. Recommendation: build a thin, versioned Stage 4.5 contribution protocol now (record types + publication functions + AMB `data_issues` placement + applicable gates), defer the formal monad layer to the pre-V1 specification per the user's earlier decision, and leave the registry parser, R1AssemblyCalc, and the full gate suite to the later R1 module.

### 1.1 Reader — present, not immutable

The fuller context is `CalculationRequest` (`types.ts:1154`: `participantKey`, `participantHistory`, `provisionTimeline: PlanVersionTimeline`, `measurementDate: DateString | null`, `measurementBasis`, `calculationKind`, `formulaId`, `roundingConfig`, `tolerance`, `runContext`). The narrow formula-level context is `CalcContext` (`types.ts:1473`) with only 3 fields (`planVersionId`, `measurementDate`, `rounding: RoundingSpec`) — far narrower than spec §1.1, which also wants participant inputs, historical rules, source references, and assumptions in the context. Context is passed explicitly as the first argument everywhere: `FormulaOperation = (ctx: CalcContext) => CalcResult<…>` (`compose.ts:62-64`); ~30 formula functions take `ctx: CalcContext` (`formulas.ts:167,193,305,…`); pipeline stages take `state: PipelineState` and read `state.request`. Gap: no `Readonly<Context>` or `Readonly<RunState>` anywhere in `src/`; immutability is by convention (spread copies), not enforced by type. Only `ReadonlyArray`/`ReadonlySet` uses exist (`decisions.ts:118`, `validation.ts:768,3147`).

### 1.2 State — present in shape, not spec `RunState`

`PipelineState` (`types.ts:1205`) carries `request` + 10 nullable stage slots (`provisions`, `eligibility`, `service`, `compensation`, `baseBenefit`, `protectedBenefit`, `restrictedBenefit`, `roundedBenefit`, `normalRetirementBenefit`, `reconciliation`) + `trace: CalculationTrace` + `missingInputs: MissingDataItem[]`. Threading is by spread copy: `initialState` (`pipeline.ts:417`); `appendSteps` returns a new object (`pipeline.ts:435-437`); `runExactPath` (`pipeline.ts:1717`) reassigns a local `let state` with spread copies (`pipeline.ts:1746-1833`). Stage functions return `{output, steps} | StageFailure` (e.g. `identifyProvisions`, `pipeline.ts:450`). Pinning is present: `InputSnapshot` (`types.ts:272`: `snapshotHash`, `entityVersions`, `planVersionIds`, `formulaIds`, rule/formula/tolerance versions); `createInputSnapshot` (`model.ts:413`); `CalculationRun` (`types.ts:1019`, pins `inputSnapshot`, `inputSnapshotHash`, `ruleVersion`, `engineVersion`); `RunContext` (`types.ts:1550`). A second, case-level state machine exists: `CaseAnalysisState` (`decisions.ts:1805`: `inputSnapshot`, `planProvisions`, `participants`, append-only `auditLog`, `advisoryWorkList`). ## 3. What's genuinely new in the spec

1. **WorkProductLog as a monoidal Writer (§1.5, §9.3).** The engine has an ordered trace (`CalculationTrace`) but no log type carrying `traceEvents[]/findings[]/fragments[]/evidenceRefs[]/warnings[]/decisions[]/openIssues[]`, no associative append/merge, no empty identity log, no deduplication by stable ID, no conflict escalation. This is the single biggest missing piece.
2. **FindingPublicationCalc (§2.9) + the §7.2 record types.** `EvidenceRef`, `Finding`, `NarrativeFragment`, `WorkProductContribution` — all 0 matches in `src/`. The engine's `Finding` (`validation.ts:108`) is a rule-check record, not a publishable finding; its `Provenance` (`types.ts:131`) is single-level, not the spec's two-level provenance (primary evidence + interpreting work product).
3. **The shared WorkProductLedger (§7.1) + WorkProductContributionCalc (§2.10).** No ledger, no contribution package, no publish/ingest function. The `CasePackage` (`types.ts:297`) holds all products' records in one case file, but that is a case container, not a ledger of versioned contributions.
4. **R1 template section registry + R1AssemblyCalc (§2.11, §8).** Entirely absent — and correctly so for PA_AMB; this is the later R1 module's work. Includes the topic-key registry, the collector→reconciler→renderer pipeline (§9.1), the dependency DAG + incremental refresh (§9.2), and the G1–G14 gates (§10) as an assembly-time suite.
5. **Citation rules (§7.3, §7.4).** No `imageViewerDocumentNumber` field anywhere in `src/`; no "Image Viewer document number pending" handling; no citation builder with dedup-by-identical-reference and preservation of distinct page/cell citations. The engine's `SourceLocation` (`types.ts:73`) records where a value came from, but it is not a citation system.
6. **Two-level provenance (§7.3).** `Provenance` has one `documentId` + a `derivation` string. The spec requires both the primary evidence and the interpreting work product, as separate linked records, with four identifier kinds (Drive file ID, local filename, internal evidenceId, Image Viewer document number) never substituted for one another.

Not new: the six effects in plain form, the ten-stage pipeline, the composition engine (`Compose`/`Protect`/`Limit`/`Normalize` already exist in `compose.ts`), the decision state machine, the bounds/scenarios path, the audit records, the invariants. The spec's §6 implementation direction ("small, typed, pure functional core first… keep UI/persistence/file imports at the boundary") is exactly what Stage 4 built.

## 5. Recommendation

### 5.1 Build Stage 4.5 now — the contribution protocol (thin, versioned)

The contribution protocol depends only on what Stage 4 already produces (calculations, validations, decisions, determination records), so it can be built now, before Stage 5. Building it now also fixes the contract before Stage 5 produces reconciliation/statistical findings that must conform to it. It is small: one new module, record types, publication functions, and tests.

**File-level changes (in `~/workspace/pbgc-pa-amb-analysis/src/`):**

- `src/contribution.ts` (new) — the whole protocol in one module:
  - `WorkProductLog` type: `traceEvents[]`, `findings[]`, `fragments[]`, `evidenceRefs[]`, `warnings[]`, `decisions[]`, `openIssues[]`; `emptyLog` (identity); `mergeLogs(a, b)` (associative append, deterministic ordering, deduplication by stable ID + version, conflicting values with the same semantic key escalated to an explicit review state, never silently discarded — spec §9.3).
  - §7.2 record types: `EvidenceRef` (with `evidenceId`, `sourceKind`, `imageViewerDocumentNumber: string | null` stored as text, `accessStatus: verified|available|missing|pending`), `Finding` (`findingId`, `claimType`, `reviewState: draft|reviewed|approved|superseded|disputed`, `materiality`, `intendedR1Topics` as semantic keys, `derivedFromFindingIds`, `supersedes`), `NarrativeFragment` (`fragmentId`, `findingIds`, `targetTopicKeys`, `form`, `content`, `inclusionState`, `approvalState`, `displayOrder`, `conflictGroup`), `WorkProductContribution` (`productId`, `productVersion`, `caseId`, `producedAt`, `publishedBy`, `sourceSnapshotId`, `status`, `findings[]`, `fragments[]`, `citations[]`, `warnings[]`, `requiredFollowups[]`, `downstreamDependencies[]`).

  - `assembleContribution(...)` — WorkProductContributionCalc: builds the versioned AMB contribution package from the published findings + fragments + citations + warnings + follow-ups. Includes `sourceSnapshotId` (the `InputSnapshot` hash) and the calculation-run ID.

**Tests (`test/contribution.test.ts`, new):**

- `WorkProductLog` merge: associativity (`merge(merge(a,b),c) = merge(a,merge(b,c))`), identity (`merge(empty, x) = x`), deterministic ordering, deduplication by stable ID + version, conflict escalation to review state (never silent discard).
- Finding publication: calculation → finding with evidence; validation finding → finding; determination → finding; unsupported assertion refused (no evidence, no explicit missing-evidence exception → not published as fact); `reviewState` lifecycle (`draft → reviewed → approved → superseded/disputed`).

### 5.2 What belongs to the later R1 module, not to PA_AMB

- The R1 template section registry parser (§8.1): parse the official native R1 template (shell + instructions), identify stable semantic section keys, headings, insertion anchors; preserve native styles/layout/tables/numbering/fixed text; treat section numbers as display labels; unknown sections marked for mapping, not guessed. The registry is verified against the user's selected template every time.
- `R1AssemblyCalc` (§2.11): the collector→reconciler→renderer pipeline (§9.1) — ingest contributions, validate types/citations/provenance, resolve superseded versions, group by topic/subject, detect contradictions and incompatible measurement bases, select current reviewed/approved contributions, summarize/order, render citations/tables, insert into matched anchors, produce placement/citation/omissions reports. It must not independently reinterpret source material, revise rules, change calculations, or declare approvals.
- The R1 document renderer + file adapter (§9.4): pure assembler builds a typed `DocumentModel` first; a file adapter applies insertions to a COPY of the official template. The renderer is at the side-effect boundary.
- The full G1–G14 gate suite as assembly-time tests, including G4 (valid section anchor or listed unplaced), G10 (native template structure preserved), G11 (citation index tracing each sentence/table to source IV document + location + originating product), G14 (human-authored edits preserved or conflicts flagged).
- The dependency DAG + incremental refresh (§9.2) at case level: `SourceDocument -> PlanRule -> Calculation -> Finding -> NarrativeFragment -> R1Placement -> R1Draft`; on revision, identify affected descendants, invalidate stale findings/placements, recalculate only required modules, regenerate affected sections, preserve the old approved draft and audit history.
- The `WorkProductLedger` as a case-level artifact: a versioned JSON package assembled from contributions (one file, owned by the user, consistent with the versioned case-package file as primary store — OPFS is out, Stage 3 P-04). The R1 module consumes an immutable approved snapshot of it. The ledger is not a database and not browser storage.

### 5.3 What the earlier generators (R5, DEL, 436, PF, E.Adm, E.Adj) must add later — the protocol contract

Do not redesign them here. Each module must implement this contract when its turn comes:

1. **Dual export (§11).** Every product exports BOTH (1) its traditional file (R5 `.docx`, 436 memo, etc.) and (2) a versioned, machine-readable `WorkProductContribution` package. The package is structured evidence and conclusions captured DURING the analysis, not a summary of a finished document.
2. **Record types.** Use the §7.2 types as specified in `contribution.ts`: `EvidenceRef`, `Finding`, `NarrativeFragment`, `WorkProductContribution`. Same field names, same enums (`claimType`, `reviewState`, `sourceKind`, `accessStatus`, `inclusionState`, `approvalState`), same semantic topic keys (NOT bare numbers).
3. **Two-level provenance (§7.3).** Every finding carries both the primary evidence ref and the interpreting work-product ref. Four identifier kinds (Drive file ID, local filename, internal evidenceId, Image Viewer document number) are never substituted for one another. Image Viewer numbers are text, entered/imported only from a verified source, never inferred or invented.
4. **Review lifecycle.** Findings and fragments carry `reviewState` / `approvalState`; `supersedes` links revisions; a superseded finding never silently replaces an approved one (G5). Only reviewed/approved contributions are eligible for R1 assembly; the R1 module selects, it does not approve.
5. **Materiality + destinations.** Each finding states `materiality` (explicit case-level flag/rule) and `intendedR1Topics` (semantic keys). The module decides what is material; the verified section registry determines where it belongs.
6. **Versioning.** Every package carries `productVersion`, `sourceSnapshotId`, and the calculation-run ID. A source/rule change produces a new package version; downstream placements depending on it are invalidated, not silently carried forward (G9).
7. **No silent publication.** Conflicting contributions stop silent publication of the affected assertion and identify the conflicting sources and runs (G6). Every material claim links to evidence (G1) or carries an explicit missing-evidence exception.

### 5.4 What NOT to build — the formal monad system, deferred

Do not build a `Calc<A>` type, `map`/`flatMap`/`bind` helpers, a unified `CalcError`, or a monad-transformer layer now. Reasons: (a) the spec itself (§1 NOTE) says typed functions and explicit result objects suffice and no general-purpose monad-transformer library is needed; (b) the engine already embodies all six effects in that form (§1); (c) the user's earlier decision (2026-11-11) is to build the upfront work first, then specify the shared pattern as a monad in TypeScript from five or six examples, right before V1 — the examples do not yet exist (the CaseResult monad lives in R5 only; PA_AMB's `CalcResult` is the second; V1/BSRS patterns are not yet built). The monad specification is a pre-V1 task, not a Stage 4.5 task. Likewise defer: `Readonly<Context>`/`Readonly<RunState>` enforcement (convention + tests suffice now), unifying `CalcResult` with `StageFailure` into one `Result<A, CalcError>`, and removing the 65 low-level `throw`s (the pipeline boundary is already throw-free; the contribution protocol must consume only boundary outputs, §5.1). Revisit all of these when the pre-V1 monad specification is written.

### 5.5 Sequencing

1. Fix the spec errors in §6 (small, before relying on the spec).
2. Stage 4.5: contribution protocol (§5.1) — thin, versioned, tested. Do not start Stage 5's statistics before it, because Stage 5 findings must conform to the protocol from the start; the protocol's `Finding` type is what Stage 5 publishes into.
3. Stage 5: reconciliation (Δ/D/R, `BenefitComparison` producer) + statistical engine — publishing into the protocol.
4. Later R1 module: registry parser, `R1AssemblyCalc`, renderer, full gates, ledger consumption (§5.2).
5. Pre-V1: formal monad specification from five or six examples (§5.4).
6. Earlier generators adopt the §5.3 contract one module at a time, when each is next touched — not as a big-bang retrofit.
